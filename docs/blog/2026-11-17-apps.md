Caddy Snake 0.8.0 adds `caddysnake apps`: one program that turns a machine into a place where a team builds and shares small internal web apps. Nobody writes the code by hand. Each person asks their own AI assistant, the assistant builds the app and publishes it, and the person gets an address to share.

![An assistant is asked for an app; the app appears in the dashboard and opens](/img/apps-demo.gif)

<!-- truncate -->

## Why

Every team has a list of small tools nobody has time to build: the lunch sign-up, the equipment booking sheet, the form that replaces a shared spreadsheet. An AI assistant can write any of them in a few minutes. The hard part comes after: where does the app run, where does its data live, how do colleagues open it, and what happens when the next change breaks it?

Caddy Snake already runs Python apps inside Caddy and loads new ones without a restart. Apps puts the missing pieces on top of that, so the answer to all four questions is "the server takes care of it".

## Try it

You need Python 3.13 or newer. There is nothing else to install.

```bash
pip install caddysnake
caddysnake apps
```

```text
caddy-snake apps is running.
  Open:               http://localhost:9080/
  Assistant (MCP):    http://localhost:9080/_apps/mcp
  Data folder:        ~/.caddysnake/apps
```

Give the assistant address to any assistant that can use [MCP](https://modelcontextprotocol.io) tools. With Claude Code:

```bash
claude mcp add --transport http apps http://localhost:9080/_apps/mcp
```

Then ask:

> Make an app where the team can sign up for Friday lunch.

The assistant creates the app and tells you where it is, for example `http://localhost:9080/friday-lunch/`. No AI is included or required from us: you bring the assistant you already use.

## What the server does for you

**Every app has its own address and its own data.** An app is served at `/<app-name>/` and keeps its data in a single SQLite file that the server looks after. There is no database to install, start or back up separately: a backup is a copy of one folder.

**Every save is a version.** Before a version goes live, the server builds it, checks that it starts and applies its data changes. If any step fails, the version is refused, the assistant is told why in words it can act on, and the version that was running keeps running. Any earlier version can be brought back.

**Drafts are safe places to try things.** A draft is a private copy of an app with a copy of its data, at its own address. Break it as much as you like; the live app is untouched until you publish the draft.

**The assistant gets a guide, not just tools.** When it connects, the assistant is told how apps here are built: Python, plain pages without a build step, data through the `db.py` that every new app starts with. If someone brings an app written in another language, the assistant is asked to rewrite it.

**There is a dashboard for people.** It lists the apps, their versions and logs, and it is where you manage who can sign in and which access keys their assistants use.

## Sharing with a team

On your own computer the server only listens locally. To share it, turn on sign-in:

```bash
caddysnake apps user add ana --admin
caddysnake apps --domain apps.example.com --require-login
```

With a domain, Caddy gets the HTTPS certificate on its own. `caddysnake apps install` sets it up as a service on Linux, macOS and Windows.

One thing to be clear about: this is built for a team that trusts each other. Anyone who can publish an app can run code on the server, and apps are not isolated from one another. Sign-in decides who is on the team; it is not a wall between its members. The [sharing page](/docs/apps/sharing) says exactly what is protected and what is not.

## How it is built

Apps is open source and lives in the same repository, in its own Go package, so a Caddy build with only the plugin pulls in none of it.

- **Caddy** serves everything and handles HTTPS.
- **The Caddy Snake plugin** runs each app as a dynamic Python app. This release adds what the platform needed and what is useful on its own: `mount_prefix` to serve an app under a path, `module_auto` to detect WSGI or ASGI, `memory_limit`, and replaced apps that finish their running requests first.
- **Versions** are stored with git, so an assistant that works in a terminal can clone an app and push to publish.
- **Data** is SQLite, one file per app, opened by a pure Go driver. The same 17 tools are available over MCP, an HTTP API and the command line.
